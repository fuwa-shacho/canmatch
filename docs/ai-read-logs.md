# AI読み取り記録（Issue #8）

## 保存する内容

読み取り1回につき`ai_read_logs`に1行追加する。写真の保存先パス、利用者、自販機（確定登録後）、モデル名、プロンプト版、成否、AIの生のテキスト応答、AI GatewayログID、エラー種別、修正件数を記録する。

APIキー、認証情報、リクエストの画像base64、署名付き写真URLは記録しない。生の応答は外部のAIが生成した内容なので、管理者専用の監査データとし、公開APIや利用者画面へ渡さない。

## ライフサイクル

- 登録成功: 読み取りログと自販機を関連付けて保持する。商品・価格を保存するトランザクションと同じトランザクション内で関連付ける。
- 手動登録: AIが失敗した読み取りも、登録に使った場合は自販機に関連付ける。ただし修正率の分母に含めない。
- 撮り直し・登録中断・AI判定で自販機ではない写真: 読み取りログは未登録状態で保持する。元画像は既存の削除規則を維持し、後から写真が閲覧できるとは保証しない。
- 未登録ログ: 原則30日経過後に`php artisan ai:prune-unlinked --apply`で削除する。未実行なら自動では消えないため、運用時に定期実行を設定する。`--apply`を省略するとプレビューのみ。
- 退会: 利用者に紐付く読み取りログをDB外部キーの`ON DELETE CASCADE`で削除する。自販機自体は既存仕様どおり保持するが、本人に由来する生のAI応答は残さない。
- 自販機の物理削除: 関連ログを削除する。撤去報告による非表示（#10）は物理削除ではないため記録を保持する。

## 修正件数

AIが返した正規化済み商品行と、登録時に確定した商品名・価格・温冷の組を比較する。行の並べ替えは修正に数えず、行の追加・削除・値の変更を各1件として数える（同じ行の複数項目を直しても1件）。修正率は、成功した読み取りを使って自販機登録したログのうち、修正件数が1件以上の割合とする。AI失敗後の手入力は分母に含めない。

`php artisan ai:read-stats --date=2026-10-24`で日本時間の1日分の呼び出し回数・成功・失敗・登録・修正率を表示する。

処理時間・トークン数はAI Gateway側で確認する。アプリ側の対応付けには`gateway_log_id`を使う。GeminiのレスポンスにログIDがない場合はnullを保存する。

## 導入・制約

1. 本番DBのバックアップを取る。
2. `php artisan migrate`で新テーブルを追加する。既存の自販機データには変更を加えない。
3. 関連テストと全体テストを実行し、写真投稿・登録・失敗時の手入力を確認する。
4. 未登録ログの定期削除方法を運用担当者が設定する。

既存の写真読み取りを伴う**新規登録フロー**に接続している。#46の自販機更新フローはレビュー待ちであり、更新時ログの接続は#46マージ後に別途確認・実装が必要。したがって、この状態だけで#8のすべての経路の完了を保証しない。
